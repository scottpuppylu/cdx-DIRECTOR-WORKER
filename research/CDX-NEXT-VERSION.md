# cdxdw 下一版研究建議與落地順序

以 `v2.6.0-cdx.3` 的獨立研究作為基線。已重現失敗入口被放行、舊成功覆蓋新失敗、持鎖程序終止後不能復工、編輯草稿擋住既有候選、合併後行為失敗，以及新工作樹找不到 Skill。

| 優先 | 研究建議 | .4 的做法與後續條件 |
|---|---|---|
| P0 | 候選由最近有效證據判定 | 工單版本、候選、建置工件及嘗試分開識別。AUTO、E2E、人工 REVIEW 和 PO 各有判定。舊文字依原本的證據強度顯示，需補驗才能放行。下一步用實際瀏覽器和正式候選試用。 |
| P0 | 崩潰後可查、可續 | 使用 OS 鎖，保存每次原生啟動及已知 turn ID。對帳找到活躍回合就回填 ID。回復自原生歷史的紀錄會標示事件覆蓋範圍。正式模型故障窗口仍須實測。 |
| P0 | 草稿和生效工單各自演進 | 施工、驗收和狀態查詢採最後派工快照。重派後新版本重新綁候選及證據。 |
| P1 | 驗收真正要交付的組合 | 以目標分支 SHA、依序採用的候選和合併後 SHA 留證，執行公開入口。目標、工單或選用候選改變會使通過結果過期。有 merge queue 的專案仍需接上實際 merge-group CI 證據。 |
| P1 | Desktop 工作線、接手與封存 | 可顯式登記乾淨 detached worktree，驗證 worker 端 Skill，保存聊天定位和候選 ref。已封存的候選可以重建。實際 UI Handoff、帶本機修改、移回 Local、Hook 信任及成品審查以試用驗收。 |
| P1 | 重跑隔離、獨立審查與稽核歸屬 | 本機執行來源和篩過的子程序環境已入紀錄。後續接入專案 CI 或隔離執行器，驗證檔案、憑證和工具邊界，讓 reviewer 優先取得最小規格與 diff。依需要使用上游外部 hash anchor，並報告稽核缺口。 |
| P1 | 工作線與遷移查詢 | 先用唯讀 `work status` 查生效工單、舊證據、候選和工作線。升級沿用版本化 runtime 與原資料。若未來改用資料庫，先做可重跑匯入、狀態校驗、逐線切換、原子指標與增量回復。 |
| P2 | 量測 Desktop、原生 Git 與 App Server 的摩擦 | 以新專案和既有專案試作，包含單線兩 commit、途中中斷、跨線整合失敗。量測到候選的時間、來回次數、復工步驟、錯綁、工具和有效用量。依結果決定 App Server 深度、Goals／子代理及 `codex exec --json` 或 SDK 的適用範圍。 |
| P2 | 讓包裝與狀態更精簡 | 依實際依賴與試用後產出發行 manifest 及檔案雜湊。舊版工具適合置於相容包。回合、用量、驗收分別取證，模型和 effort 以原生實際配置為準。資料庫、常駐服務和新面板由試用數據決定。 |

試用目標是零次錯綁或未授權操作，每次中斷都可判定狀態，復工最多兩個人工步驟。舊版和新版的裝置、耗時與完成證據分開記錄。
